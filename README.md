# foodbolt

Foodbolt is a mock food delivery company that uses [Spectral](https://github.com/cap-theorem/spectral) as its service discovery layer. Nothing is real (no food, no cards, no couriers, no database; all state lives in memory), but every API works, and the five services find and call each other only through Spectral.

## Services

| Service | Language | Port | Owns |
|---|---|---|---|
| `gateway` | TypeScript (Node 24) | 8080 | public API, customer auth, request tracing |
| `orders` | Java 21 | 8081 | order lifecycle, the saga that ties the others together |
| `restaurants` | Python 3.13 | 8082 | restaurant catalog, menus, quotes, kitchen tickets |
| `payments` | Go | 8083 | card authorizations, captures, voids, refunds |
| `dispatch` | Rust | 8084 | courier fleet, delivery assignment and simulation |

Every service also serves `GET /healthz` (plain `ok`), `GET /info` and `GET /v1/stats`.

## Call graph

```
client ─▶ gateway ─┬─▶ restaurants ──▶ dispatch            (browse: ETA estimates)
                   └─▶ orders ─┬─▶ restaurants             (quote, kitchen ticket, cancel)
                               ├─▶ payments                (authorize, capture, void)
                               └─▶ dispatch                (assign courier, food ready, cancel)

restaurants ──▶ orders   (async: preparing, food_ready)
dispatch    ──▶ orders   (async: courier_at_restaurant, picked_up, delivered)
```

Placing an order (`POST /v1/orders` on the gateway):

1. gateway authenticates the customer and calls `orders`.
2. orders asks `restaurants` for a quote (prices, fees, tax, prep time, pickup location).
3. orders authorizes the total with `payments`. A decline stops here with `402`.
4. orders sends a kitchen ticket to `restaurants`.
5. orders asks `dispatch` for a courier. If an instance has no free courier (`503`), orders tries another instance, up to 3 attempts. If none can take it, orders voids the payment and cancels the ticket.
6. The order comes back `confirmed`, with a `trace` of every service instance it touched.

Then the order moves on its own:

- The kitchen (`restaurants`) posts `preparing`, then `food_ready` back to the order.
- orders forwards `food_ready` to the delivery's `dispatch` instance.
- The courier drives to the restaurant (`courier_at_restaurant`), waits until the food is ready, picks it up (`picked_up`) and delivers it (`delivered`).
- On `delivered`, orders captures the payment.

Status: `confirmed → preparing → ready_for_pickup → out_for_delivery → delivered`, or `cancelled` / `payment_failed`.

## Spectral usage

Each service registers through its language's SDK (`spectral-go`, `spectral-python`, `spectral-rs`, `@cap-theorem/spectral`, `spectral-java`) and keeps its lease alive in the background, re-registering if the lease is lost.

State is in memory, so a resource lives on the instance that created it. Every instance of a stateful service registers under two names:

- `<service>` (for example `payments`): any instance, used for new work.
- `<service>/<instance>` (for example `payments/pay-91c0`): exactly this instance.

Resource ids start with the owning instance: `<instance>.<6 random base36 chars>`, e.g. order `ord-3f2a.k7x2m9`, payment `pay-91c0.a1b2c3`, ticket `rst-77de.x9y8z7`, delivery `dsp-0b4e.q1w2e3`. To act on an existing resource, a caller takes everything before the last `.` as the owner and looks up `<service>/<owner>`. If the owner is gone (its lease expired), the resource is gone with it, and the caller gets `404`.

`gateway` is stateless and registers only as `gateway`.

## Logs

Every service writes one line per event to stdout, in this format:

```
2026-11-18T20:15:03.123Z INFO order confirmed order_id=ord-3f2a.k7x2m9 total_cents=2843 courier=Maya request_id=req_5b1f0c9a2e7d4c11
```

`<UTC timestamp, ms> <INFO|WARN|ERROR> <message> key=value ...`, with values double-quoted when they contain spaces. Each service logs:

- startup (`listening port=… endpoint=…`) and Spectral registration (`registered with spectral service=… instance=…`), lease loss, and re-registration
- every inbound request except `/healthz`: `http method=POST path=/v1/orders status=201 ms=41.8 request_id=…`
- every outbound call: `call service=payments instance=pay-91c0 method=POST path=/v1/payments/authorize status=201 ms=3.2 request_id=…`
- failed lookups and retries (`WARN`)
- domain events: order placed, payment authorized, ticket ready, courier assigned, picked up, delivered, payment captured, and so on

`x-request-id` is generated by the gateway (`req_<16 hex>`) and passed on every call, including the asynchronous callbacks, so `grep req_…` across all pods shows one order's whole life.

## Configuration

| Variable | Default | Meaning |
|---|---|---|
| `SPECTRAL_ADDR` | `http://127.0.0.1:8000` | sidecar API (read by each SDK) |
| `PORT` | per service | listen port |
| `ADVERTISE_URL` | `http://<own IP>:<PORT>` | endpoint other services use to reach this instance |
| `SERVICE_NAME` | per service | base name registered with Spectral |
| `INSTANCE_ID` | `<prefix>-<4 hex>` | unique instance name (`gw`, `ord`, `rst`, `pay`, `dsp`) |
| `LEASE_TTL_SECONDS` | `5` | lease length |
| `MACHINE` | hostname | label shown in traces |
| `TIME_SCALE` | `1.0` | multiplies every simulated duration (prep, travel); `0.2` is 5x faster |

`payments` also reads `PAYMENTS_FAILURE_RATE` (default `0`): the fraction of authorizations that fail with `503` to simulate a flaky processor. `dispatch` reads `COURIERS` (default `6`): the courier fleet size per instance.

## Shared shapes

Error body from internal services: `{"error": "message"}` (payments adds `decline_code`).

A hop, returned in `hops` by every synchronous internal call:

```json
{"service": "payments", "instance": "pay-91c0", "machine": "node-2", "latency_ms": 3.214}
```

`/info`:

```json
{"service": "payments", "instance": "pay-91c0", "machine": "node-2", "endpoint": "http://10.0.0.12:8083", "uptime_s": 312}
```

Money is integer cents (USD). Locations are `{"lat": 37.7936, "lng": -122.3958}`. Times are RFC 3339 UTC strings.

## API: gateway (public, port 8080)

Every `/v1` route needs `Authorization: Bearer <token>`. Demo customers (in memory):

| Token | Customer | Default address | Default payment method |
|---|---|---|---|
| `fb_test_alice` | `cus_alice` Alice | 1 Market St (37.7936, -122.3958) | `pm_card_visa` |
| `fb_test_bob` | `cus_bob` Bob | Dolores Park (37.7596, -122.4269) | `pm_card_mastercard` |
| `fb_test_carol` | `cus_carol` Carol | Golden Gate Park (37.7694, -122.4862) | `pm_card_amex` |
| `fb_test_dave` | `cus_dave` Dave | Twin Peaks (37.7544, -122.4477) | `pm_card_declined` |

| Route | Calls |
|---|---|
| `GET /v1/me` | none: the customer profile |
| `GET /v1/restaurants` | `restaurants GET /v1/restaurants?lat=&lng=` with the customer's address |
| `GET /v1/restaurants/{id}` | `restaurants GET /v1/restaurants/{id}` |
| `POST /v1/orders` | `orders POST /v1/orders` |
| `GET /v1/orders/{id}` | `orders/<owner> GET /v1/orders/{id}` (404 if it belongs to another customer) |
| `POST /v1/orders/{id}/cancel` | `orders/<owner> POST /v1/orders/{id}/cancel` |
| `GET /v1/couriers` | `dispatch GET /v1/couriers` (one instance's fleet) |

`POST /v1/orders` body:

```json
{"restaurant_id": "tacos-el-rayo", "items": [{"item_id": "al-pastor-taco", "quantity": 3}], "tip_cents": 300}
```

`dropoff` (`{"lat", "lng", "address"}`) and `payment_method` are optional and default to the customer's. The gateway adds `customer_id`.

Gateway responses are the downstream JSON with `request_id` and `trace` added (`trace` = the gateway's hop followed by the downstream `hops`; `hops` itself is removed). Gateway errors look like:

```json
{"error": {"code": "payment_declined", "message": "card_declined"}, "request_id": "req_…"}
```

Mapping: missing or bad token `401 unauthorized`; downstream `400/422` → `400 invalid_request`; `402` → `402 payment_declined`; `404` → `404 not_found`; `409` → `409 conflict`; Spectral has no instance, connection refused, or `5xx` → `503 service_unavailable`.

The gateway serves `GET /v1/stats` and `GET /info` without auth.

## API: orders (Java, port 8081)

`POST /v1/orders`

```json
{"customer_id": "cus_alice", "restaurant_id": "tacos-el-rayo",
 "items": [{"item_id": "al-pastor-taco", "quantity": 3}],
 "dropoff": {"lat": 37.7936, "lng": -122.3958, "address": "1 Market St"},
 "payment_method": "pm_card_visa", "tip_cents": 300}
```

`201` with the order. Errors pass through from restaurants (`404`, `409`, `422`), a decline is `402 {"error", "decline_code", "order_id"}` (the order is kept as `payment_failed`), and no courier anywhere is `503`.

The order:

```json
{
  "order_id": "ord-3f2a.k7x2m9",
  "customer_id": "cus_alice",
  "status": "confirmed",
  "restaurant": {"id": "tacos-el-rayo", "name": "Tacos El Rayo", "pickup": {"lat": 37.7599, "lng": -122.4148}},
  "lines": [{"item_id": "al-pastor-taco", "name": "Al Pastor Taco", "quantity": 3, "unit_price_cents": 450, "line_total_cents": 1350}],
  "subtotal_cents": 1350, "delivery_fee_cents": 199, "service_fee_cents": 135, "tax_cents": 116, "tip_cents": 300, "total_cents": 2100,
  "dropoff": {"lat": 37.7936, "lng": -122.3958, "address": "1 Market St"},
  "payment": {"payment_id": "pay-91c0.a1b2c3", "method": "pm_card_visa", "status": "authorized"},
  "ticket_id": "rst-77de.x9y8z7",
  "delivery": {"delivery_id": "dsp-0b4e.q1w2e3", "courier": {"id": "dsp-0b4e.c3", "name": "Maya", "vehicle": "scooter"}, "eta_seconds": 41},
  "placed_at": "2026-11-18T20:15:03.120Z",
  "updated_at": "2026-11-18T20:15:03.162Z",
  "timeline": [{"at": "2026-11-18T20:15:03.162Z", "event": "confirmed", "source": "orders", "detail": "courier Maya on a scooter"}],
  "hops": [...]
}
```

The order's `total_cents` is the quote's `total_cents` plus `tip_cents`, and that is the amount authorized. `hops` is only in the `POST /v1/orders` response (orders' own hop, then the quote, payment, ticket and delivery hops in call order).

`GET /v1/orders/{id}` returns the order, or `404`. `GET /v1/orders` lists this instance's orders, newest first (`{"orders": [...]}`, up to 50).

`POST /v1/orders/{id}/cancel` is allowed while the status is `confirmed`, `preparing` or `ready_for_pickup`. It voids the payment, cancels the ticket and the delivery, and returns the order with status `cancelled`. Otherwise it returns `409`.

`POST /v1/orders/{id}/events`, used by restaurants and dispatch:

```json
{"event": "food_ready", "source": "restaurants", "detail": "ticket rst-77de.x9y8z7 ready"}
```

| event | from | new status | side effect |
|---|---|---|---|
| `preparing` | restaurants | `preparing` | |
| `food_ready` | restaurants | `ready_for_pickup` | `dispatch/<owner> POST /v1/deliveries/{delivery_id}/ready` |
| `courier_at_restaurant` | dispatch | (none) | |
| `picked_up` | dispatch | `out_for_delivery` | |
| `delivered` | dispatch | `delivered` | `payments/<owner> POST /v1/payments/{payment_id}/capture` |

Statuses only move forward (`confirmed < preparing < ready_for_pickup < out_for_delivery < delivered`); a late event is still added to the timeline. Returns `202 {"order_id", "status"}`, `404` for an unknown order, and `409` if the order is cancelled.

## API: restaurants (Python, port 8082)

The catalog is built in, and every instance has the same copy. Kitchen tickets live on the instance that accepted them.

`GET /v1/restaurants?lat=&lng=` returns `{"restaurants": [...], "hops": [...]}`. Each entry is `{"id", "name", "cuisine", "rating", "open", "location", "prep_seconds", "delivery_fee_cents"}`. When `lat` and `lng` are given, restaurants calls `dispatch POST /v1/estimates` and adds `distance_km` and `eta_seconds` (prep plus travel) to each entry, sorted by `eta_seconds`. If dispatch is unavailable, it logs a warning and returns the list without ETAs.

`GET /v1/restaurants/{id}` returns the restaurant plus `"menu": [{"item_id", "name", "description", "price_cents", "available"}]`, or `404`.

`POST /v1/quotes` with `{"restaurant_id", "items": [{"item_id", "quantity"}]}` returns:

```json
{"restaurant": {"id", "name", "pickup": {"lat", "lng"}},
 "lines": [{"item_id", "name", "quantity", "unit_price_cents", "line_total_cents"}],
 "subtotal_cents", "delivery_fee_cents", "service_fee_cents", "tax_cents", "total_cents",
 "prep_seconds", "hops"}
```

`service_fee_cents` is 10% of the subtotal, rounded. `tax_cents` is 8.625% of the subtotal, rounded. The total covers subtotal, delivery fee, service fee and tax. Errors: unknown restaurant `404`, closed `409`, unknown or unavailable item or `quantity` outside 1..20 `422`.

`POST /v1/tickets` with `{"order_id", "restaurant_id", "lines": [{"item_id", "name", "quantity"}]}` returns `201 {"ticket_id", "status": "accepted", "ready_in_seconds", "hops"}`. The kitchen then:

- after 1s × `TIME_SCALE`: status `preparing`, posts `preparing` to `orders/<owner of order_id> POST /v1/orders/{order_id}/events`
- after `prep_seconds` × `TIME_SCALE` (from acceptance): status `ready`, posts `food_ready`

Callbacks retry up to 3 times, 1 second apart. They stop on `404` or `409`.

`GET /v1/tickets/{id}` returns `{"ticket_id", "order_id", "restaurant_id", "status", "lines", "created_at"}`. `POST /v1/tickets/{id}/cancel` sets `cancelled` and stops the kitchen. Both return `404` if unknown.

## API: payments (Go, port 8083)

`POST /v1/payments/authorize` with `{"order_id", "customer_id", "amount_cents", "payment_method"}`:

- `201 {"payment_id", "order_id", "status": "authorized", "amount_cents", "payment_method", "created_at", "hops"}`
- `pm_card_visa`, `pm_card_mastercard`, `pm_card_amex` approve.
- `pm_card_declined` → `402 {"error": "card declined", "decline_code": "card_declined"}`.
- `pm_card_insufficient_funds` → `402` with `decline_code` `insufficient_funds`.
- Any method approves only up to 50000 cents; above that it is `402` `amount_too_large`.
- An unknown method or `amount_cents <= 0` → `400`.
- With probability `PAYMENTS_FAILURE_RATE` → `503 {"error": "processor unavailable"}`.
- Authorizing the same `order_id` twice on one instance returns the existing payment (`200`).

`POST /v1/payments/{id}/capture`, `/void` and `/refund` move `authorized → captured`, `authorized → voided` and `captured → refunded`. They return the payment, `404` if unknown, and `409` on an invalid transition. Repeating the transition the payment is already in returns `200` unchanged. `GET /v1/payments/{id}` returns the payment.

`GET /v1/stats`: counts by status, plus `authorized_cents` and `captured_cents`.

## API: dispatch (Rust, port 8084)

Each instance runs its own fleet of `COURIERS` couriers, named deterministically from a fixed list (Maya, Diego, Priya, Sam, Jordan, Lena, Kenji, Ana, Omar, Zoe, Theo, Ines), with vehicles cycling `bike`, `scooter`, `car`, and starting at fixed spots within about 3 km of (37.7749, -122.4194). Courier ids are `<instance>.c<n>`.

Travel time is `max(3, distance_km / speed) × TIME_SCALE` seconds, using haversine distance and a speed in km per second: bike 0.15, scooter 0.2, car 0.25.

`POST /v1/estimates` with `{"dropoff": {"lat", "lng"}, "pickups": [{"id", "lat", "lng"}]}` returns `{"estimates": [{"id", "distance_km", "travel_seconds"}], "hops"}`, using scooter speed plus a 5 second handoff.

`POST /v1/deliveries` with `{"order_id", "pickup", "dropoff", "ready_in_seconds"}`:

- Picks the nearest idle courier and returns `201 {"delivery_id", "order_id", "status": "assigned", "courier": {"id", "name", "vehicle"}, "eta_seconds", "hops"}`. `eta_seconds` is `max(travel to pickup, ready_in_seconds) + travel to dropoff`.
- If no courier is idle, it returns `503 {"error": "no courier available"}`.

The delivery then runs on its own, posting each step to `orders/<owner of order_id> POST /v1/orders/{order_id}/events`:

1. The courier travels to the pickup and posts `courier_at_restaurant`.
2. It waits for the food to be ready (`POST /v1/deliveries/{id}/ready`).
3. It posts `picked_up`, travels to the dropoff, and posts `delivered`.
4. The courier becomes idle at the dropoff.

Callbacks retry the same way as restaurants'. A cancelled delivery frees its courier right away.

`POST /v1/deliveries/{id}/ready` (`202`), `POST /v1/deliveries/{id}/cancel` (returns the delivery, `409` once delivered), `GET /v1/deliveries/{id}`, and `GET /v1/couriers` (`{"couriers": [{"id", "name", "vehicle", "status": "idle|to_pickup|waiting|to_dropoff", "location", "delivery_id"}], "hops"}`).

## Run it locally

```bash
make up
```

```bash
make order
```

```bash
make logs
```

`make up` builds every image and starts a stand-in sidecar (`dev/spectral-stub`, which implements the sidecar HTTP contract with one shared directory) and two instances of every service except the gateway. `make order` places an order as Alice and prints it. `make track ID=<order_id>` follows it until it is delivered. `make directory` shows what is registered.

## Run it in Kubernetes

```bash
kubectl apply -k deploy/k8s
```

Every pod runs its service next to its own `spctrld`, as a native sidecar (an init container with `restartPolicy: Always`, so the sidecar starts first and stops last). The service keeps the default `SPECTRAL_ADDR=http://127.0.0.1:8000` and advertises `http://$(POD_IP):<port>`. The sidecars bootstrap from `spctrld-peers.spectral.svc.cluster.local:7000` (the `spectral` namespace from the Spectral repo); change `--bootstrap` and the `spctrld` image in `kustomization.yaml` to match your cluster.

Only the gateway has a Kubernetes Service. Everything else is found through Spectral.

```bash
kubectl -n foodbolt port-forward svc/gateway 8080:80
```

```bash
kubectl -n foodbolt logs -f deploy/orders -c orders
```
